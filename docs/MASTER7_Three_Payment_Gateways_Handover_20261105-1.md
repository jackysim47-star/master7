## 2. Payment gateway到底是什么

Payment gateway（支付网关）是连接平台与支付处理系统的技术入口，负责安全传递付款请求和支付结果。有些供应商同时提供网关、收款处理和结算服务，实际服务范围以商户合同与官方资料为准。

在本项目中要分清：

| 层次 | 负责什么 | 不能据此证明什么 |
|---|---|---|
| MASTER7前台 | 展示渠道、提交客户付款意图、展示服务器确认的订单状态 | 看到付款成功页面不证明账本已正确入账 |
| MASTER7后台 | 查询订单、核对流水、处理授权范围内的管理事项 | 后台HTML 200不证明本人登录和管理权限通过 |
| MASTER7服务端／内部integration gateway | 调用供应商、验证结果、更新自身订单、记录证据 | 进程健康或configured=true不证明外部商户已连通 |
| VPay／GSPAY／1MPay | 按各自官方协议提供支付相关能力 | 三家不能共用未经核实的签名算法、字段和成功码 |
| 银行／电子钱包等付款渠道 | 按对应渠道完成资金处理 | 用户付款凭证不等于商户最终结算记录 |
| MASTER7账本／数据库 | 保存客户余额变化、订单和审计记录 | 网页上余额数字变化不证明真实收款或可恢复备份 |
| Render | 托管应用及提供部署、日志、指标 | Render live不等于支付、短信或游戏通过验收 |

**客户付款成功、客户平台余额入账、支付公司向商户结算，是三个需要关联核对的事件。**“结算未验证”不自动等于每笔客户付款失败；反过来“开关打开”也不能证明任何一笔付款成功。

## 6. 收款从客户到平台账本的完整流程

下述是目标流程要求，不代表已经执行：

1. 客户已按平台规则登录，选择一家渠道与MYR金额。
2. 服务端校验客户身份、权限、金额、币种和当前维护状态；身份与金额不能只信前端。
3. 服务端先持久保存本地订单、唯一请求标识、渠道与环境，再准备对外建单。严禁只存在内存或临时JSON。
4. 使用该家供应商的真实协议建单；密钥仅留服务器端。
5. 保存供应商订单号、准确建单结果和可追踪引用；向客户返回允许公开的付款链接／二维码。
6. 客户完成付款；浏览器返回页只展示服务端确认的状态，不能自行决定入账。
7. 供应商向正式配置的HTTPS通知地址发送结果；服务端先按该家规则验证真实性，再关联对应商户、环境、渠道和订单。
8. 核对金额、币种、唯一订单号与最终支付状态。资料冲突、缺失、无法验证或仍处理中时，保留未确认状态，不能加余额。
9. 收到合法成功结果后，在可靠数据库事务中完成唯一一次账本记录、余额变动和订单入账标记。
10. 重复通知／查单／人工核查并发进入同一逻辑，仍只能入账一次。
11. 后台可关联本地订单、供应商订单与入账流水；客户看见的状态与账本一致。
12. 按供应商记录及银行结算资料完成对账，分别标记客户付款、客户账本和商户结算的状态。

服务端通知与主动查单互补。究竟何时必须查单、以何种状态为准，应由每家官方协议确定，不能用另一家实现推测。

## 7. 建议的内部状态设计

以下状态名仅是设计建议，接手时先对照已有实现，不要求为了改名字迁移现有资料。

| 维度 | 示例状态 | 必须保证 |
|---|---|---|
| 对外建单 | not_sent／creating／created／create_unknown／rejected | 网络超时属于结果不明，不直接重复建单 |
| 支付状态 | pending／succeeded／failed／expired／unknown | 中间状态、失败与成功须依供应商协议映射 |
| 平台入账 | not_posted／posted／review_required | 支付成功和已入账分开，避免崩溃时漏账或重复入账 |
| 商户结算 | unverified／pending／reconciled／discrepancy | 与客户付款及钱包入账分开 |
| 维护权限 | 本地允许／本地关闭 | 关闭新订单时仍应按设计处理已存在订单的可信通知与对账 |

“付款链接生成成功”只对应建单阶段；“供应商受理”不一定是付款最终成功。收到过期或失败消息后，也不能不看官方规则就覆盖既有最终成功状态。退款／撤销需有独立的受控账务流程，不能修改或抹掉历史流水。

## 8. 超时、重复、乱序与异常怎么处理

| 场景 | 必须实现的行为 |
|---|---|
| 建单请求超时 | 标记结果不明，利用原唯一请求标识及官方查单／幂等规则确认；不能盲目再建另一笔 |
| 客户反复点击付款 | 相同请求去重，不能形成重复订单或重复扣款 |
| 浏览器关闭、断网或未返回 | 依可信服务端结果处理；不能依赖客户打开成功页 |
| 相同通知重复到达 | 验证后识别已处理事件／业务交易，重复回复按官方协议，不重复入账 |
| 不同事件对应同一笔付款 | 业务订单和账本也要唯一保护，不能仅按通知事件ID去重 |
| 两个并发通知同时成功 | 数据库唯一约束与事务保证只有一次账本更新 |
| 通知合法但订单金额／币种不符 | 不入账，记录差异并交受控核查 |
| 通知无法验真 | 不更新付款成功状态、不加余额；脱敏记录原因 |
| 供应商已收款，数据库写入失败 | 持久记录待处理事项，恢复后安全重试；不能把供应商成功丢掉 |
| 已入账后通知重发或查单重复确认 | 继续显示原入账记录，不产生第二笔余额 |
| 数据库故障／磁盘满 | 停止依赖不可靠状态的新处理，保留订单与事件，不靠临时文件假装已记账 |
| 通知丢失／积压 | 按官方规则对未决订单补查并对账；没有证据不能自动标失败 |
| 渠道维护 | 停止新建单；已付订单、通知和对账不得被简单丢弃 |
| 退款／撤销／出款失败 | 独立规则、独立状态、追加账务记录；不得直接删历史订单或改写旧流水 |

通知确认回复与持久化处理必须协调：先确保已可靠接收，再按供应商要求及时确认。不能在事件没有持久保存且处理也未完成时无条件回复成功，导致对方不再重试。

### 证据最小格式

每一项填写：

- 供应商、产品、环境；官方协议版本与来源；
- 验收时间（Asia/Kuching）、代码SHA、部署ID；
- 用例编号、预期结果、实际结果；
- 脱敏本地订单引用、供应商订单引用、通知／查单核验结果；
- 平台唯一入账记录及前后台对应证据；
- 结算是否另行完成；若未完成，保持未验证；
- 通过／失败／受限／未执行；剩余阻碍、负责人、下一步。

订单号等证据可在授权私有系统中核对，公开报告仅给脱敏引用。截图不能包含密钥、银行个人资料或登录令牌。
