# MASTER7 Operations

营运时区：`Asia/Kuching`（MYT，UTC+8）
金额币种：MYR；财务金额使用整数 sen 或固定两位小数。

## 每日操作

1. 打开后台 Dashboard，确认 Database、SMS、Payment checks 和 Game checks 状态。
2. 首次打开后台只加载摘要和当前面板；需要哪一项才点击对应菜单。手动刷新只刷新当前面板，避免整页重复读取大量记录。
3. 先处理待审核银行转账、提款、客服单与安全告警；资金操作必须关联会员、订单、金额和后台流水。
4. 每日 MYT 00:00 后核对前一日充值、提款、福利、佣金与净现金流；月、半年和年度报表从同一账本汇总。
5. 渠道或厂家出现超时、状态冲突或金额不符时，保持订单待复核，不手工重复入账。
6. 新广告、福利或银行户口先保存草稿，再由 Owner 检查前台显示、有效期和规则。
7. 支付与游戏总开关最后处理；公司银行受控测试、真实福利/广告发布和对应厂家 E2E 未完成前保持关闭。

## 健康与告警

- Portal health：`https://master7-v17-staging.onrender.com/health`
- Gateway health：`https://master7-integration-gateway.onrender.com/health`
- 资金通知在后台有新充值或提款记录时播放提示音；浏览器必须先由员工点击页面以允许音频。
- 提示音可在后台顶栏关闭或打开；首次开启可试听。轻量事件接口只返回事件类型、ID 和游标，不返回姓名、金额、银行、账号或银行单。
- 青色慢速状态灯表示当前选中菜单或健康检查状态。灯光和 `LIVE` 字样属于操作提示，不是支付或游戏生产验收凭证。
- 监控 HTTP 5xx、应用 error/fatal、数据库状态、登录失败突增、待处理订单积压和供应商超时。
- 状态灯只代表对应检查结果；`LIVE` 或绿色灯不能单独证明资金或游戏已生产验收。

## 人工银行转账审核

1. 已登录且已批准的会员从前台 Deposit 进入后，才可选择公司银行户口、复制户名和账号、上传银行单并提交。
2. 客户端在网络失败、超时或页面刷新后复用同一会员与金额的请求键；不要通过重复点击建立新订单。明确成功、重置或更改金额后才建立新请求。
3. 银行单按比例完整缩放；后台必须核对整张收据、实际银行流水和金额，不能只看客户上传图片。
4. 同一订单只能由一个审核请求取得 claim。重复页面、双击或两名员工并发处理时，其余请求应收到 `409 Deposit already reviewed`。
5. 批准后再核对钱包只增加一次；拒绝不增加钱包。创建/修改银行资料、提交、批准和拒绝都必须有同事务审计。
6. Audit log 只显示配置 ID 或订单 ID；不得在 Audit 写入账号、户名或银行单内容。

## 大名单与推广

- 联系人文件由浏览器按 1 MiB 分块读取，每 1,000 条上传一次；不要把 600,000 条一次复制到页面文本框。
- 后端以短期导入锁、持久计数和多行 UPSERT 处理每批资料，并强制最多 600,000 条；电话号码会标准化及数据库去重，已经退订的联系人不能被后续导入恢复成已同意。
- CSV 发布名单只导出 `opted_in`，每页 2,000 条按 `(created_at,id)` 游标流式输出，最多 600,000 条。
- 发布前先用非真实号码文件做分级压测；当前自动测试没有代表 600,000 条已在生产数据库完成吞吐验收。
- 真实 WhatsApp/SMS 发送前必须具备正式 provider、获批模板、联系人的有效同意、速率与配额、失败重试和退订处理。平台当前的 Share/CSV 功能不代表免费群发服务已经接通。
- 每次正式活动先用内部获授权号码小批量验收内容、图片、Referral link、退订和统计，再按 provider 批准的速率扩大。

## 支付运行规则

- GSPAY MYR Deposit 依官方建单、Get Payment 与 callback 合约实施；只有状态返回 `orderReady=true` 且 Owner 开启对应渠道时才允许提交。当前仍关闭。
- GSPAY Payment callback 当前配置为 `https://master7.best/api/payment/gspay/callback`；`master7.best` 的 302 URL Forwarding 必须改为 Render 直接域名或保留 POST 的反向代理。
- GSPAY 的 2 分钟付款链接与 10 分钟无回调拒绝不能代替独立查单；过期 QR/URL 不得重用。
- 1MPay 只有正式环境。字段映射与成功 ACK 已确认，但不得用自动化测试发真实资金；正式 E2E 必须由 Owner 明确安排受控金额并保存银行、订单、回调、钱包与对账证据。
- 每家公司独立检查 Connected、Order、Query、Callback、Wallet 和 Reconcile。
- 任一阶段未验收时，渠道保持 Suspended/Closed，不能用浏览器返回页增加钱包余额。
- 回调、独立查单和账本必须绑定同一商户、会员、订单、金额、币种与厂家流水。
- 重复、乱序、并发通知只能产生一笔会员账和一笔相反的 provider-clearing 分录。
- Deposit、客户提款/Payout 与商户 Settlement 分开验收和对账。
- 当前厂家待确认项目见 `PAYMENT_VENDOR_MESSAGES_ZH.md`；GSPAY、VPay 与 1MPay 各自独立验收。

## 福利、Turnover 与公司广告

- 不完整福利允许保存草稿；公开前必须有正数奖励、唯一一项正数 Turnover 规则、适用的最低存款、领取次数和有效期。百分比奖励还必须设置最高奖励。
- 当前福利模块负责规则验证、计算与客户展示，`walletCreditAutomation=false`；没有已验证领取账本和合资格交易时不得把规则写成自动派发。
- 公司广告启用前必须有有效标题和图片；目标链接如填写，只接受 HTTPS。未取得正式素材时保持草稿。
- 禁止用假银行资料、假福利条款或占位广告公开给会员。

## 游戏运行规则

- 目录、图片、按钮状态、真实启动与钱包分别检查。
- 转账钱包记录进入前余额、转入引用、厂家余额、退出引用和回主钱包结果。
- 无缝钱包按下注、派彩、取消事件逐笔验真与幂等处理。
- 维护、断线、重复退出和未结局保留可复核状态；未完成时不把游戏标为可玩。

## 备份与恢复

- 升级前保存应用提交、部署包 SHA-256、数据库快照或加密备份及当前开关。
- 先在隔离环境恢复，核对表数、记录数、外键、会员、余额、未结订单和账本。
- 回滚必须同时考虑应用版本、数据库兼容性和正在投递的回调；不得只回滚页面。
- 密码、OTP、API key、银行资料和私钥只能存放在受控秘密管理或加密备份中。

## 发布顺序

1. 本地测试、lint 与 production build。
2. 提交并推送准确分支；记录 commit、bundle SHA-256 和 Render deploy ID。
3. Render 显示 live 后检查 health、数据库、入口、Owner 只读登录、支付/游戏关闭状态和日志。
4. 厂家端到端验收逐家进行；完成一家公司只打开该公司的已签收能力。
5. 更新 `CURRENT_DEPLOYMENT.md`、验收 CSV 与恢复回执，再由 Owner 做最终签收。
